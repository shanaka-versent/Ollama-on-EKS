Why so many components? (Design rationale)

The system is designed this way for three reasons:

  1. Users never see Cognito's hosted UI. The built-in Cognito login pages are functional but ugly and inflexible. The custom login portal (login.html) provides a polished experience while the auth_proxy Lambda handles all Cognito interactions server-side. This means the portal can handle first-time password changes, MFA enrollment with QR codes, and forgot-password flows — all without ever redirecting the user to a Cognito-branded page.
  2. Defense in depth. Each layer catches different threats. WAF stops bots and DDoS. The CloudFront Function catches unauthenticated requests before they hit the origin. Cognito handles identity. Open WebUI enforces role-based access. No single layer can be bypassed to gain full access.
  3. Separation of concerns. The login portal, API key portal, and GPU control panel are separate Lambda functions with separate IAM roles. The key_manager Lambda cannot access EKS. The gpu_controller Lambda cannot write to DynamoDB. If one Lambda is compromised, the blast radius is contained.

Step-by-Step Walkthrough

  1. The user opens the platform URL in their browser. This hits CloudFront, which is the only public-facing endpoint.
  2. The CloudFront Function (auth_redirect) runs on the viewer-request event. It checks for a cookie named token. Since this is a new user, no cookie exists.
  3. The CloudFront Function returns a 302 redirect to /auth/login.html. The user's browser follows the redirect.
  4. CloudFront serves login.html from the S3 login portal bucket. This is a single-page application (SPA) with two tabs: "Sign In" and "Request Access".
  5. The user clicks the "Request Access" tab and fills in their name, email, and a password (12+ characters, mixed case, numbers, symbols).
  6. The login page's JavaScript calls the Cognito SignUp API directly from the browser. This uses the "public" app client (no client secret required for signup). The call goes directly to cognito-idp.ap-southeast-2.amazonaws.com — it does NOT go through the auth_proxy Lambda.
  7. Cognito triggers the pre_signup Lambda. This Lambda does two things: (a) sets autoConfirmUser and autoVerifyEmail to true so the user does not need to verify their email address separately, and (b) publishes a notification to the SNS topic with the user's email and instructions for the admin.
  8. The admin receives an email notification with the subject "Ollama WebUI — New Access Request" containing step-by-step instructions to approve the user.
  9. The user sees a success message: "Account created, wait for admin approval." They cannot log in yet because they are not in any Cognito group.
  10. The admin goes to the AWS Cognito Console, finds the user, and adds them to a group — either user (standard access) or admin (full access).
  11. When the admin adds the user to a group, CloudTrail logs the AdminAddUserToGroup API call. An EventBridge rule matches this event and triggers the access_granted Lambda.
  12. The access_granted Lambda looks up the user's email from Cognito and sends an SES email with the subject "Access Granted" containing the login URL and the assigned role.
Why auto-confirm? The pre_signup Lambda auto-confirms users so they do not receive a separate "verify your email" step. Since access is controlled by Cognito group membership (not just having an account), there is no risk in skipping email verification — a user with an unverified email but no group membership still cannot access anything.
SES Sandbox Note If SES is in sandbox mode, the "Access Granted" email will only be delivered if the recipient's email address is verified in SES. In production, request SES production access to send to any email.

Returning user login — Phase 1 (API challenge detection) + Phase 2 (server-side hosted UI for OAuth)

The Two-Phase Approach Explained

The login uses a two-phase strategy because of a fundamental constraint: Open WebUI requires an OAuth authorization code to issue its session JWT, but the Cognito API (InitiateAuth) does not produce OAuth authorization codes — it produces Cognito tokens directly.

Phase 1: Challenge Detection (Cognito API)

The Lambda calls InitiateAuth with USER_PASSWORD_AUTH. This is fast and tells us immediately if the user needs to change their password (NEW_PASSWORD_REQUIRED), set up MFA (MFA_SETUP), or enter a TOTP code (SOFTWARE_TOKEN_MFA). For first-time users, this is the only phase needed — see Section 4.

Phase 2: OAuth Token Exchange (Hosted UI Scraping)

For returning users with MFA, the Lambda drives Cognito's hosted UI server-side to complete the full OAuth authorization code flow. This is necessary because Open WebUI's /oauth/oidc/callback endpoint expects an authorization code, not a raw Cognito token. The Lambda:

  1. Starts the OAuth flow by hitting Open WebUI's /oauth/oidc/login endpoint, capturing the owui-session cookie and the Cognito /authorize redirect URL.
  2. Follows the redirect chain to Cognito's login form, extracts the CSRF token.
  3. Submits the user's credentials (and TOTP code) to the hosted UI forms.
  4. Captures the resulting authorization code in the callback redirect.
  5. Calls Open WebUI's callback with the auth code and the owui-session cookie, which triggers Open WebUI to exchange the code for tokens and return a token cookie (the session JWT).
Why not just use the Cognito API tokens? Open WebUI is configured as an OAuth/OIDC client. It expects the standard OAuth flow: redirect to provider, user authenticates, provider redirects back with an authorization code, app exchanges code for tokens. If we bypassed this and injected Cognito tokens directly, Open WebUI would not create a session — the user would appear logged out. Driving the hosted UI server-side is the only way to get a valid Open WebUI session token while keeping the user on a custom login page.

What Gets Stored in the Browser

After a successful login, two things are stored:

  • token cookie (HttpOnly, Secure, SameSite=Lax) — The Open WebUI session JWT. This is what the CloudFront Function checks. Because it is HttpOnly, JavaScript cannot read it, protecting against XSS token theft.
  • token in localStorage — The same JWT value, stored by the login page's JavaScript. This is used by the API key portal and GPU control panel to send as a Bearer token in the Authorization header. localStorage is accessible to JavaScript on the same origin only.
Why store the token in both places?

The HttpOnly cookie protects the session from XSS (malicious scripts cannot steal it). But the API key portal and GPU control panel need to send the token in an Authorization: Bearer header to their Lambda backends. Since JavaScript cannot read HttpOnly cookies, the token is also stored in localStorage for this purpose.

This is a deliberate tradeoff: localStorage is vulnerable to XSS, but the portal pages are static HTML served from S3 with no user-generated content, making XSS unlikely. The cookie provides the primary session protection for the main application.

First-time login — password change + MFA enrollment (no Cognito hosted UI involved)

Step-by-Step Walkthrough

  1. The admin creates a user in Cognito with a temporary password. Cognito sends the user an email with their temporary credentials.
  2. The user enters their email and the temporary password on the login page.
  3. The auth_proxy Lambda calls Cognito's InitiateAuth API. Cognito responds with a NEW_PASSWORD_REQUIRED challenge.
  4. The Lambda returns {status: 'new_password_required'} to the login page, which shows a "Set New Password" form. The Cognito session is base64-encoded and sent to the client as an opaque state token.
  5. The user sets a new password (minimum 12 characters, must include uppercase, lowercase, numbers, and symbols).
  6. The Lambda calls RespondToAuthChallenge with the new password. Cognito responds with an MFA_SETUP challenge.
  7. The Lambda calls AssociateSoftwareToken to generate a TOTP secret. This returns a base32-encoded secret code.
  8. The Lambda returns the secret and a otpauth:// URI to the login page. The page generates a QR code client-side (using a JavaScript QR library) from the URI format: otpauth://totp/OllamaWebUI:{email}?secret={secret}&issuer=OllamaWebUI
  9. The user scans the QR code with their authenticator app (Google Authenticator, Authy, 1Password, etc.).
  10. The user enters the first 6-digit code displayed by the authenticator app.
  11. The Lambda calls VerifySoftwareToken with the TOTP code. If valid, Cognito returns STATUS: SUCCESS.
  12. The Lambda also attempts RespondToAuthChallenge for the MFA_SETUP challenge. This step is best-effort and non-fatal — the TOTP device is already registered after VerifySoftwareToken succeeds.
  13. Setup is complete. The user is redirected to the Sign In tab to log in normally with their new password and MFA.
Key Design Decision The VerifySoftwareToken call registers the TOTP device regardless of whether RespondToAuthChallenge(MFA_SETUP) succeeds. This means if the challenge response fails (e.g., session expired), the user's authenticator app is still linked and they can sign in normally. This avoids the frustrating scenario where a user scans the QR code but then has to redo it.

How the Portal (API Keys) Works

The API key portal lets authenticated users generate API keys for programmatic access to the Ollama inference API. The portal relies on the Open WebUI session token (JWT) for user identity — it does not have its own authentication system.

Token chain — from localStorage through to DynamoDB

How It Works

  1. During login, the login.html JavaScript stores the Open WebUI JWT in localStorage under the key token.
  2. When the user navigates to /portal/, CloudFront serves the static index.html from S3. The CloudFront Function does not check authentication for /portal/* paths — the portal handles its own auth via the token.
  3. The portal JavaScript reads localStorage.getItem('token') to get the JWT. If no token is found, it shows a "Please log in first" message with a link to the login page.
  4. The portal sends requests to /portal/api/keys with the JWT as a Bearer token in the Authorization header.
  5. CloudFront routes /portal/api/* to API Gateway, which invokes the key_manager Lambda.
  6. The Lambda decodes the JWT payload using base64url decoding (it splits the JWT on ., takes the middle segment, and decodes it). It extracts the id (or sub) and email fields.
  7. The Lambda queries DynamoDB for API keys belonging to this user_id and returns the list.
Why no JWT signature verification?

The key_manager Lambda decodes the JWT payload without verifying the signature. This is a deliberate design choice:

  • The Lambda is only reachable via CloudFront + API Gateway. Direct API Gateway access is blocked by the origin lockdown (shared Referer secret).
  • CloudFront only sends requests from clients that reached the CDN, and the login portal is the only page that sets the Authorization header.
  • Adding JWT signature verification would require the Lambda to fetch Open WebUI's JWKS (JSON Web Key Set), adding latency, complexity, and a dependency on Open WebUI being available.
  • The trust boundary is: "If the request reached this Lambda through the CloudFront + API Gateway chain with a valid-looking JWT, the user is authenticated."

How GPU Control Works

The GPU control panel allows admin users only to start, stop, and check the status of GPU nodes. This is important because GPU nodes cost money ($0.35–$1.90/hr), and idle nodes should be stopped to save costs. KEDA handles automatic scale-to-zero, but sometimes admins need manual control.

How Admin Verification Works

  1. The portal JavaScript sends the user's JWT (from localStorage) as a Bearer token in the Authorization header.
  2. The gpu_controller Lambda extracts the token and calls Open WebUI's API at GET /api/v1/auths/ with the same token.
  3. Open WebUI validates the JWT and returns the user's profile including their role field. This role is synced from Cognito groups on every login.
  4. If the role is admin, the Lambda proceeds with the GPU operation. If not, it returns a 403 Forbidden response.
  5. For Kubernetes operations, the Lambda generates a short-lived EKS bearer token using STS presigned URLs — this is the standard mechanism for programmatic EKS access from Lambda.
Why verify via Open WebUI instead of decoding the JWT? The Open WebUI JWT contains only id, exp, and jti — it does NOT contain the user's role or email. The role is stored in Open WebUI's database and synced from Cognito groups on login. The only way to check the role at runtime is to call Open WebUI's API. Results are cached for 5 minutes per Lambda container to avoid timeout issues during status polling.

Password reset is handled entirely by the custom login portal. Users click "Forgot password?" on the login page, receive a verification code via email, then enter the code and a new password. No Cognito hosted UI is involved.

Security Details

  • User enumeration prevention: The Lambda always returns {status: 'code_sent'} even if the email does not exist in Cognito. This prevents attackers from discovering which emails have accounts.
  • Rate limiting: Cognito enforces rate limits on the ForgotPassword API. If too many requests are made, the Lambda returns a 429 Too Many Requests error.
  • Code expiry: Verification codes expire after a configurable period (default: 1 hour). Expired codes return a clear error message.
  • MFA preserved: Resetting the password does not affect MFA enrollment. The user logs in with their new password and existing authenticator app.

Open WebUI Role Management

Cognito is the single source of truth for user roles. Open WebUI syncs roles from Cognito groups on every login, meaning any group changes in Cognito take effect the next time the user logs in.

How It Works

When a user completes the OAuth login flow, Open WebUI receives an ID token from Cognito that contains a cognito:groups claim (a list of groups the user belongs to). Open WebUI maps these groups to internal roles using environment variables:

Environment VariableValueEffect
ENABLE_OAUTH_ROLE_MANAGEMENT true Roles are synced from the OAuth provider (Cognito) on every login. Without this, roles are only set on first login
OAUTH_ADMIN_ROLES admin Users in the Cognito "admin" group get Open WebUI admin role
OAUTH_ALLOWED_ROLES admin,user Only users in these Cognito groups can log in. Users not in any listed group are rejected
DEFAULT_USER_ROLE user Users who pass the group gate are auto-activated with "user" role (no manual approval in Open WebUI needed)
ENABLE_PASSWORD_AUTH false Hides Open WebUI's built-in password change form. All password management is via Cognito (through the custom portal)
ENABLE_ADMIN_CHAT_ACCESS false Admins cannot view other users' chat history
ENABLE_ADMIN_EXPORT false Database export is disabled for all users including admins

What if an attacker steals a session token from localStorage?

If an attacker manages to steal the JWT from localStorage (e.g., through an XSS vulnerability on a page that shares the origin):

  • They can use the token to access the API key portal and generate API keys for the stolen user's account.
  • They can use the token to chat with the LLM as the stolen user (if they also set it as a cookie).
  • They cannot start/stop the GPU unless the stolen user is an admin (the gpu_controller Lambda verifies the role via Open WebUI's API).
  • The token expires after approximately 1 hour. After expiry, it becomes useless.
  • Mitigation: The portal pages are static HTML served from S3 with no user-generated content, making XSS extremely unlikely. Content Security Policy headers further restrict script execution.

Troubleshooting

Common issues and their solutions. Each issue includes the symptom, root cause, and fix.

Login and Access Issues

"Redirected to login page when clicking Generate API Key"

Symptom: User is logged into Open WebUI but clicking the "Generate API Key" banner or visiting /portal/ shows a "Please log in" message.

Root Cause: The portal reads the Open WebUI JWT from localStorage. If the user logged in before the localStorage storage was implemented (or logged in via a different mechanism), the token might not be in localStorage.

Fix: Log out of Open WebUI and log back in via the custom login page (/auth/login.html). The new login flow stores the token in both the HttpOnly cookie and localStorage.

"MFA code rejected" or "Invalid code"

Symptom: The 6-digit TOTP code from the authenticator app is rejected.

Root Cause: TOTP codes are single-use and time-based (30-second windows). If you entered a code that just expired or was already used in a failed attempt, it will be rejected.

Fix: Wait for a new code to appear in your authenticator app (the 30-second timer resets) and try again. Also check that your device's clock is accurate — TOTP relies on synchronized clocks.

"Access denied" after admin approved the account

Symptom: The admin added the user to a Cognito group, but the user still cannot log in or sees "Access Denied".

Root Cause: Open WebUI syncs roles from Cognito groups on login. If the user was already logged in when the group was changed, the role is not yet synced.

Fix:

  1. Verify the group assignment in Cognito Console — make sure the user is in the user or admin group (not a typo like "User" or "users").
  2. Have the user log out completely and log back in. The new login will fetch updated group claims from Cognito.
Slow page load after login (10-20 seconds)

Symptom: After logging in, the first page load takes 10-20 seconds. Subsequent loads are fast.

Root Cause: VPC Origin cold start. CloudFront connects to the internal NLB via VPC Origins, which involves establishing a private connection. The first request after a period of inactivity incurs this startup cost.

Fix: This is expected behavior. Subsequent requests use the established connection and load in under 1 second. Static assets (JS, CSS, images) are cached at the CloudFront edge with CachingOptimized policy, so only the initial HTML document experiences the delay.

"Session expired" during MFA or password change

Symptom: While entering a new password or TOTP code, the user gets "Session expired. Please sign in again."

Root Cause: Cognito sessions for multi-step challenges (password change, MFA setup) expire after approximately 3 minutes. If the user takes too long, the session becomes invalid.

Fix: Start the login process again from the beginning. The sessions are intentionally short-lived for security.

API Key Issues

API key returns 403 Forbidden

Symptom: Using the API key with x-api-key header returns 403.

Possible Causes:

  1. Key is expired: Check the key's expiry date in the portal. The expiry_checker Lambda disables expired keys automatically.
  2. Key is disabled: Check if the key was manually disabled via the portal's toggle switch.
  3. Key is revoked: Revoked keys cannot be re-enabled.
  4. Wrong endpoint: API keys work on /v1/* paths (e.g., /v1/chat/completions), not on /portal/* or /api/* paths.
"Access Granted" email not received

Symptom: Admin added the user to a Cognito group, but the user did not receive the "Access Granted" email.

Root Cause: SES is in sandbox mode, and the recipient's email is not verified in SES.

Fix: Either verify the recipient's email in SES (for sandbox mode) or request SES production access. Check CloudWatch logs for the access_granted Lambda to see the exact SES error.

GPU Control Issues

GPU start returns "403 Forbidden: Admin access required"

Symptom: Clicking "Start GPU" returns a 403 error.

Root Cause: The user's role in Open WebUI is not "admin". The gpu_controller Lambda verifies the role by calling Open WebUI's API.

Fix: Ensure the user is in the Cognito admin group (not just user). The user must log out and log back in after the group change.

GPU shows "starting" for a long time

Symptom: The GPU status stays on "starting" for more than 5 minutes.

Root Cause: Karpenter may be unable to provision a GPU node (no spot capacity, quota limit reached, or wrong instance type).

Fix: Check Karpenter logs: kubectl logs -n kube-system -l app.kubernetes.io/name=karpenter. Common issues: (1) GPU spot quota is 0 vCPUs (request increase via Service Quotas), (2) spot capacity unavailable in the AZ, (3) NodePool limits reached.
